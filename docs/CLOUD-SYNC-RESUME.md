# Cloud photo sync resume and progress — 18 October 2026

Fixes the repeated JPEG encoding after restarting Windows with an already uploaded warehouse.

- Local SQLite stores source SHA-256 → optimized JPEG SHA-256 pairs, scoped to the JPEG policy and Sharp/libvips versions. No original or optimized image copies are stored in this cache. Each request still reads and hashes the original bytes, so changed files cannot pass solely because their name, size or modification time matches.
- Existing installations warm this cache on their first verification after updating. Thereafter unchanged photos require no JPEG encoding, including after an actual process restart. Photos already identical to the Cloud JPEG can be verified directly by their byte hash.
- Missing uploads are prioritized across every catalog page. Cloud ready assets are the durable upload checkpoint. Pausing or closing the application does not discard completed uploads; uncertain upload responses are still downloaded and hash checked before registration.
- The localhost API advertises bounded bulk verification; the frontend uses batches of 32 with at most two concurrent decoders. Older desktop APIs retain the individual-image fallback. No new public Cloud endpoint, RLS change, authentication bypass or Storage overwrite is introduced.
- Presence updates are sent only where the last read Cloud presence differs, avoiding redundant events for thousands of unchanged photos. Final identity, physical-source revision, Storage and stock-integrity checks remain mandatory. This is faster reconciliation, not a promise of zero latency or a replacement for final integrity verification.
- Progress separates catalog reading, photo processing, final verification, cleanup, completion, pause and error. It shows processed/total photos, remaining, new uploads, retained/reused, missing sources and elapsed time. 100% photo processing does not announce completion before final verification.

Regression coverage includes a fresh child process using the persisted cache, original replacement with restored timestamps, malformed/oversized/duplicate/out-of-stock bulk requests, and the actual CloudSettings component with 3,106 photo IDs (3,057 ready, 49 missing). The component test verifies missing uploads first, 96 bulk verification calls instead of 3,057 individual JPEG requests, repeat sync without duplicate upload, progress before final integrity approval, concurrent folder changes, offline/reconnect and physical deletion. Cloud transport fixtures do not constitute acceptance on the owner's laptop or iPhone.
